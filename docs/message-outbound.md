# 统一消息出口

业务代码通过 `internal/outbound.Sender` 发送消息，不再直接调用 NapCat/OneBot 的发送 API。

当前链路：

```text
业务模块 -> outbound.Hub -> outbound.OneBot -> napcat.Client -> QQ
```

`Hub` 的默认平台是 `qq`，因此现有只保存群号或用户号的订阅无需迁移。需要明确平台的新路由可以在 `outbound.Target.Platform` 中指定平台名。

统一的是业务内容和投递入口，不是各平台最终显示形式。每个适配器通过 `Capabilities` 声明图片数量、图文混排、视频独立发送、富文本和卡片能力；`Plan` 根据能力拆分消息，平台适配器再渲染最终格式。

新增平台时应：

1. 实现 `outbound.Sender`；
2. 在启动组装处向 `Hub.Register` 注册平台适配器；
3. 在适配器内把 `internal/message.Segment` 转换成目标平台的消息格式。

NapCat 客户端仍负责 OneBot WebSocket 连接和 QQ 入站事件。它不再作为业务模块的消息出口依赖。飞书、Telegram 等适配器不应放进 `internal/napcat`。

## 平台策略

- QQ：允许图文混排；当前按每批最多 9 张图片的保守策略拆分；视频始终单独发送；不依赖网页链接自动生成业务卡片。
- 飞书：应使用官方 `post` 富文本或 `interactive` 消息卡片，而不是发送任意 HTML。图片、视频等资源要先上传并取得平台 key，再引用到消息或卡片中。
- 卡片由平台适配器主动渲染。微博、Weverse、直播等业务只提供标题、正文、来源链接和媒体语义，不负责拼飞书 Card JSON。

图片数量等限制应保留为适配器能力参数，经过真实账号联调后调整，不散落在各业务模块中。

## 飞书配置

管理面板的「消息出口」分组提供飞书开关、App ID、App Secret、上传并发、群路由和私聊路由。群路由格式为 `QQ群号=飞书chat_id`，多条可使用逗号或换行分隔。例如：

```text
123456789=oc_a123,987654321=oc_b456
```

启用后，原有发往这些 QQ 群的订阅会继续发送 QQ，并镜像到对应飞书群。飞书使用原生 `interactive` 卡片；图片并发上传并缓存资源 Key，视频和音频在通知卡片之后发送。卡片失败时降级为纯文本，媒体失败不会吞掉正文通知。

抖音私信、登录二维码等原本发给 QQ 管理员的私聊通知，可配置 `管理员QQ号=飞书open_id` 私聊路由同步投递。

## 消息模型

`internal/message` 提供平台无关的文本、图片、视频、语音、提及和分享片段。OneBot 适配器负责将通用的 `mention`、`mention_all`、`audio` 等语义转换为 OneBot 的 `at`、`record` 等协议片段。

现有消息构造代码可渐进迁移到该模型；出口边界已经统一，迁移过程不会改变 QQ 投递链路。
